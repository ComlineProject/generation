# comline-conformance

The codegen conformance corpus and the harness that runs a generator over it.
Rollout step 3 of `design/runtime-repo-structure.md`.

Each fixture in `src/lib.rs` is one package as hand-built `Vec<FrozenUnit>`s
(not parsed - the corpus pins IR shape, not parser behaviour). `src/harness.rs`
is the generator-agnostic half: given a `Generator` (its entry point, its
`SUPPORT` table, its `VERSIONS`) it runs the generator over every fixture, at
each of its version boundaries, and diffs the output against golden files.

## Where the generators and their goldens live

Not here. A generator is a repository of its own
([`comline-rust`](https://github.com/ComlineProject/comline-rust),
[`comline-typescript`](https://github.com/ComlineProject/comline-typescript))
that depends on this crate and runs the harness in its own test suite, against
goldens it holds under `codegen/tests/golden/<fixture>/<lang>[@<boundary>]/`.
The dependency goes one way: a generator depends on generation, generation
depends on core, and nothing here depends on a generator. So a change to core
is pinned in generation, then in each generator, and nowhere does it come back.

What stays here is what needs no generator: the corpus itself, the harness, and
the tests of what every generator shares on the requests they get
(`tests/dependency_protocols.rs`, `tests/nested_protocols.rs`).

A generator wires the harness up like this (see either repo's
`codegen/tests/conformance.rs`):

```rust
const GENERATOR: Generator = Generator {
    language: "rust",
    generate: comline_codegen_rust::generate_rust,
    register: comline_codegen_rust::register,
    support: comline_codegen_rust::SUPPORT,
    versions: comline_codegen_rust::VERSIONS,
};
```

and calls `harness::corpus_matches_golden`, `harness::support_is_proven` and
`harness::the_protocol_generates_what_the_generator_does`. In the generator's
repository:

```sh
cargo test -p comline-codegen-rust --test conformance                    # check
CONFORMANCE_BLESS=1 cargo test -p comline-codegen-rust --test conformance # regenerate goldens
```

A blessed golden is **a snapshot of what the generator does now**, not a
statement of what it *should* do. When a generator changes, the diff shows up in
that change's PR and the golden is re-blessed deliberately.

A change to a fixture here changes every generator's output for it, and shows
up as drift in each generator's suite when it pins the new revision: the
generator's PR carries the new goldens.

## Feature support

Each generator states what it implements in its `SUPPORT` table
(`comline_codegen::features`), and `support_is_proven` checks every claim
against this corpus:
- a **supported** or **partial** feature has a fixture that uses it, generates,
  and matches its golden (and, where the feature can be taken out, generates
  differently without it);
- an **ignored** one generates exactly what it would without the feature;
- an **unsupported** one is refused, with an error naming the feature.

A claim no fixture can back fails the suite, so a new feature comes with a
fixture. The result is written to the generator's own `FEATURES.md` and
`features.json` at its repository root, regenerated by the same
`CONFORMANCE_BLESS=1` run as its goldens.

See `ComlineProject/docs` → Design → *The `core` ↔ target contract*.
